## 步骤 3：安全防护

**已完成**，每一条都有对应测试：

* **SQLi**：全部查询用 `?` 占位符（`app/db.py`、`app/auth.py`、`app/api.py`），
  没有任何字符串拼接 SQL；`?search=` 还额外转义了 `%`/`_` 通配符。
* **XSS**：`app/security.py::escape_deep` 对所有出站字符串做 HTML 转义，
  外加 CSP / nosniff / X-Frame-Options。
* **认证**：bcrypt（cost 12，随机盐）+ HS256 JWT（`exp`/`iss`/`jti`），
  `token_required` 校验签名与过期后**再从数据库取一次用户**；只接受 HS256，
  因此 `alg:none` 伪造被拒；登录失败对"用户不存在"和"密码错误"返回同一响应。

验证：`tests/test_security.py` 里直接跑 `' OR '1'='1`、`' UNION SELECT …`、
`'<script>alert(1)</script>'`、`alg:none`、过期 token 等载荷。

## 步骤 8、9：根因与修复

**已完成**，写在 `vulnerability/README.md`（英文，可直接进报告），要点：

* **根因**：Elasticsearch 的 `_search` 支持 `script_fields`，脚本由节点自己在 JVM 里
  编译执行。1.2 之前 `script.disable_dynamic` 默认是 `false`，没有沙箱（MVEL 表达式
  可直达 `java.lang.Runtime`），而 1.x 又完全没有认证——任何能连上 9200 的人一个 POST
  就能以节点身份执行命令。本质是"把代码当作普通数据字段"的访问控制失败（CWE-284），
  不是漏写一行校验；所以后来所有修复都是在"收回这个能力"。
* **为什么会是 root**：镜像里节点以 root 启动，命令一执行就是最高权限。
* **修复**：① 配置层 `script.disable_dynamic: true`；② 升级到 1.4.4（1.2 起默认关闭，
  1.4 有 Groovy 沙箱）；③ 设计层不把脚本能力暴露给客户端（网络 ACL、反代过滤
  `script`/`source`、或使用已移除动态脚本的 2.x）。
  补充：1.4.4 后来又被 CVE-2015-1427（Groovy 沙箱绕过）打穿，所以最稳的仍是"根本不
  接受客户端脚本"，这也正是报告里强调设计层的原因。
